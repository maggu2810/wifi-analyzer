# Internationalization (i18n)

## Two kinds of text

| Kind | Examples | Lives in | Mechanism |
|---|---|---|---|
| **Domain text** | field labels ("Group Cipher"), enum names ("CCMP-128" stays, "reserved", "Personal"), summary labels ("WPA2/WPA3-Personal (transition)"), diagnostics ("length 3 is below minimum 4") | `libs/wifi-analyze/i18n/` | gettext `.po` catalogs compiled into C++ tables |
| **App chrome** | buttons, menus, settings, onboarding, CLI help | each frontend | Android `res/values*/strings.xml`; CLI: English only for now; Qt later `.ts` |

Domain text belongs to the library because it is generated by the library (thousands of
field names across all elements) and must read the same in every frontend. Duplicating
it in `strings.xml` would scatter it and break every time a decoder is added.

## Library design

- Every user-visible domain string is defined **where it is used**:
  `WA_TR(rsn_group_cipher, "Group Data Cipher Suite")` – a stable snake_case key and the English
  text. The macro yields `MessageId::rsn_group_cipher`; the key doubles as JSON field key.
- `tools/gen_i18n_catalog.py` scans `libs/wifi-analyze/src` at build time (like xgettext),
  checks that a key always has the same text, and generates `message_id.hpp`, the constexpr
  catalogs and `messages.pot` (template for translators) into the build tree.
- Translations: `libs/wifi-analyze/i18n/<locale>.po` (msgctxt = key, msgid = English,
  msgstr = translation). Empty or outdated translations fall back to English per message;
  placeholder mismatches fail the build. No runtime gettext/ICU dependency.
- Diagnostics carry arguments; messages use positional placeholders (`{0}`, `{1}`).
- Technical identifiers are **not** translated: cipher/AKM names (CCMP-128, SAE), standard
  names (802.11ax, Wi-Fi 6), units. These are `Text` literals instead of messages.
- API: `localizer("de_DE.UTF-8")` → German catalog with English fallback;
  `available_locales()`.

To translate: build once, copy entries from `build/<preset>/libs/wifi-analyze/generated/messages.pot`
into the `.po` file, fill `msgstr`, rebuild.

## Flow to the frontends

- **JSON** (CLI `--format json`, JNI): contains both the stable `key`s and the `label`s
  rendered in the requested locale, so consumers can either display directly or map keys.
- **CLI:** locale from `--lang` or `LC_ALL`/`LC_MESSAGES`/`LANG`, default English. CLI's own
  messages (usage, errors) stay English in v1.
- **Android:** passes the app's current locale (per-app language setting supported) on each
  decode call; re-decodes (cheap) when the locale changes.

## Languages

v1: English; German exists for a few messages and is completed in M4. Adding a language = adding
a `.po` file, no code change.
